How pitchzazz actually hears
and re-pitches a voice

Every audio block runs through three DSP stages: detect the pitch, quantize it to the nearest note in scale, shift the signal there. A real-time engine keeps that from glitching, and a hot-swap mechanism can change which shift algorithm is running mid-performance. This notebook covers the windowing, the transforms, the actual formulas behind each stage. Every math card links to the exact source line on GitHub.

The real-time engine

The OS calls the audio callback on a hard deadline: one buffer's worth of time. Miss it and it drops audio as an audible glitch. The callback only pushes or pops a lock-free queue. Detect, quantize, and shift happen on a separate worker thread with no deadline of its own, so none of the normal audio-thread rules apply there.

why each one is fatal
blocka mutex, file I/O, or sleep. The callback simply doesn't return in time, no matter how briefly it was going to block for
allocatenew, a growing Vec/vector. The allocator can itself take an internal lock or walk a free list; worst case is unbounded
lockany mutex, even uncontended. If the other side is ever preempted while holding it, the audio thread stalls waiting on a thread the OS isn't scheduling

The detector needs a fixed-size block (2048 samples) to run its FFT against. Hosts don't owe you that. A DAW can hand the callback 64, 128, or 512 samples depending on its own buffer setting, and can change its mind mid-session.

01 · detectcore path

Finding the pitch: autocorrelation, normalized

A pitched sound is periodic. Its waveform repeats every T samples, where T is the pitch period. Take a copy of the signal, slide it sideways by some lag τ, and ask whether the copy looks like the original again. For almost every τ the answer is no. But the moment τ equals the true period T (or a whole multiple of it), the shifted copy lines back up with the original almost exactly, because that's what "periodic" means. Try every possible τ and measure how well each shifted copy matches. The τ with the best match, past the trivial τ=0 case, is the pitch period. That measuring is autocorrelation. Normalizing it so it's comparable at every τ is the McLeod Pitch Method's own contribution, covered further down.

why the formula looks like this
1. square itx[n]−x[n+τ] can land negative or positive. Squaring makes every difference count as positive, and makes big mismatches count far more than small ones (a difference twice as large contributes four times as much)
2. normalize by energya raw difference score alone is meaningless. A loud passage and a quiet one score very differently at an equally good match, and different τ naturally have different energy in their windows regardless of periodicity. Dividing by m(τ), the energy actually present at that τ, turns the raw mismatch into a fraction of available energy, comparable across every τ. That division turns the raw difference into NSDF.
3. every τ at onceO(·) describes how the worst-case cost grows as input size N grows. Literally sliding a copy and comparing at every τ costs O(N²). For this project's N=4096, that's ~16.8 million operations. Computing every τ's score at once via FFT costs O(N log N) instead. 4096×log₂(4096) = 4096×12 ≈ 49,000 operations. About 340× less work, for the exact same set of numbers.
the math
energy gateE = Σ x[n]²: skip the block entirely if E < 0.15
autocorrelationACF(τ) = IFFT( |FFT(x)|² ): Wiener–Khinchin, O(N log N) instead of O(N²)
energy termm(τ) = Σ x[n]² + Σ x[n+τ]²  (left window energy + right window energy)
NSDFnsdf(τ) = 2·ACF(τ) / m(τ): bounded to [−1, 1], comparable across every τ
peak choicefirst τ past the initial positive run where nsdf(τ) > 0.1, not the tallest peak
sub-sample refinefit a parabola through (−1,y₀), (0,y₁), (1,y₂) around the peak, solve the vertex
period → frequencyf = sampleRate / τ. The whole search above exists to find the true τ, the pitch period in samples; once it's found, this one division is the actual frequency

02 · quantizecore path

Snapping to the scale: outward search, ties go low

Twelve pitch classes, wrapped into an octave. If the detected note is already in the scale, it passes through untouched. If not, the search walks outward by semitone. One below, one above, two below, two above. Until it lands on one that belongs. This is genuinely two separate steps. A detected frequency is continuous (say, pitch-class 3.7, a fractional value), so it gets rounded to the nearest chromatic semitone first, with ordinary rounding, completely independent of the scale. Only that already-integer result ever reaches the search below. Anything that rounds straight into the scale never touches it at all.

the math
1. round to chromaticnote = round(hzToMidi(freq)): ordinary nearest-integer rounding, before the scale is ever consulted
2. pitch classpc(note) = ((note mod 12) + 12) mod 12: the extra +12 handles negative notes safely
3. membershipif scale.contains(pc(note)): return note unchanged
4. search orderfor d in 1..6: check pc(note−d), then pc(note+d). First match wins, below beats above on a tie

03 · hot-swapcore path

Changing engines live, with no dropout

In the actual plugin, swapping from the phase vocoder to TD-PSOLA mid-performance is one pick from the Engine dropdown, instant, no pause, no click. This section covers the mechanism that makes that possible. One atomic pointer exchange, picked up by the worker thread between blocks, never mid-process(), with the outgoing engine's warmed-up internal state cross-faded out instead of just discarded.

the math
both engines runfor crossfadeBlocks = 4 blocks (≈185ms @ 44.1kHz/2048), old and new both process the same input
equal-power blendgainOld = cos(θ), gainNew = sin(θ), θ ramped 0→π/2 continuously across the whole window
why it's exactly 1sin²θ + cos²θ ≡ 1 for any θ. The Pythagorean identity, using the same angle both times.
gain vs. powerthe blend itself is linear in amplitude (gainOld·old + gainNew·new, no squaring anywhere in the code). But scaling a signal's amplitude by g scales its power by g², and power is what predicts the blended signal's loudness
the assumptionconstant power only follows if the two engines' outputs are roughly equal-power and uncorrelated, so their powers add without a cross-term. True enough for two algorithms independently processing the same input, the standard crossfade assumption for two independent, roughly equal-power sources
why not linearlinear (1−t)/t dips below full power mid-transition (gainOld²+gainNew² < 1); equal-power keeps the sum exactly 1 throughout

04 · shiftdeep dive

Three engines, three genuinely different mechanisms

Once the target note is known, something has to actually move the pitch there. Pitchzazz ships three hot-swappable engines, each solving this with unrelated physics: one reasons about frequency, one about time-domain grains, one about playback rate. This is where the real windowing and math show up hardest.

Phase Vocoder (frequency domain)

Take the signal into the frequency domain with an FFT, then move each bin's content to a new bin scaled by the pitch ratio. Relocating spectral content is the pitch shift. The phase math below just keeps that relocation sounding coherent instead of smeared.

Live demo below: drag the slider. It recomputes bin′ = round(k · shift) for 12 source bins in real time and redraws where each one actually lands.
the math
shift ratioshift = 2^(semitoneShift / 12)
phase differenceΔφk = (φk[t] − φk[t−1]) − k·(2π/oversampling)
unwrap (qpd trick)fold Δφk into (−π, π] by subtracting the nearest even multiple of π
true frequencyωk = k·(2π/oversampling) + Δφk · oversampling: per-bin, per-frame
bin relocationbin′ = round(k · shift): magnitude and ωk both move here
phase accumulationφ′k[t] = φ′k[t−1] + hop·ωk: persists across frames, the fix for "phasiness"
where latency comes fromframeSize samples, the nearest power of two to windowSizeMs · sampleRate / 1000. A full analysis frame has to fill before the first FFT can even run, so this is a hard floor. Measured real pipeline latency: 23.22ms / 21.33ms / 21.33ms (44.1 / 48 / 96kHz), matching the formula exactly, no extra delay hiding in the block-accumulation stage

TD-PSOLA (time domain, grain-based)

No FFT at all. Cut the signal into small windowed grains, one centered on each detected pitch period, then paste them back down at new positions. Closer together to raise pitch, farther apart to lower it. Each grain's own content never changes, only its spacing does.

the math
synthesis spacingspacing = periodSamples / shiftRatio. Denser for a shift up, sparser for a shift down
grain half-widthhalfWidth = periodSamples · grainWidthMultiplier. Multiplier of the unshifted period, so formants survive
read positionreadMark = floor(synthesisMarkPos / periodSamples + ε) · periodSamples, using floor specifically to bound lookahead
where latency comes fromlatencySamples = 2 · maxHalfWidthSamples, the worst-case grain half-width at minHz, the lowest pitch this engine supports. Fixed regardless of whatever note is actually playing, since latency that fluctuated with the detected pitch would make host delay-compensation wrong mid-performance. Measured real pipeline latency: 31.29ms / 31.25ms / 31.25ms (44.1 / 48 / 96kHz), matching the formula

Varispeed + WSOLA (stretch, then resample)

The odd one out: pitch changes by genuinely changing playback rate, like varispeed-ing a tape reel, formants included, on purpose. Two stages: WSOLA stretches the signal in time, pitch-preserving. A resample then plays that stretched signal back at the inverse ratio, tape-style, changing duration and pitch together. Duration cancels, since the resample undoes WSOLA's own stretch. Pitch doesn't, since WSOLA never touched it, so the full shift survives at the original duration.

Time-stretch: WSOLA

Resampling

Cubic Hermite (Catmull-Rom) fits a curve through four neighboring samples and reads it at the target position. Linear is cheaper but dulls highs and stairsteps at extreme ratios. Windowed-sinc is the correct band-limited choice, but its width scales with ratio, costing real per-sample latency this engine's fixed budget doesn't have. Catmull-Rom is the real-time middle ground, FluidSynth's own sample interpolation among them: a fixed 4-tap kernel, cheap, allocation-free, with its own mild roll-off and self-aliasing at extreme ratios, left alone the way tape and vinyl varispeed never anti-aliased either.

the math
splice scoreNCC(offset) = Σ(a·b) / √(Σa² · Σb²): normalized cross-correlation, capped to a 256-sample window
deviate only ifNCC(offset) > NCC(0) + 0.02, a hard margin on the required improvement
resamplep(t) = 0.5·[2p₁ + (p₂−p₀)t + (2p₀−5p₁+4p₂−p₃)t² + (3p₁−3p₂+p₃−p₀)t³]
read rateread position advances by shift = 2^(semitoneShift/12) samples per output sample
where latency comes fromon paper: windowSizeSamples + searchRadiusSamples + kernelLookahead ≈ 26.6ms at 44.1kHz, fixed and ratio-independent since neither WSOLA's search window nor the resampler's kernel depends on shift amount. Measured real pipeline latency runs higher: 33.97ms / 30.21ms / 30.19ms (44.1 / 48 / 96kHz). That gap is disclosed here, still unexplained

05 · qualitydeep dive

How clean can we get?

Every artifact claim on this page so far has been qualitative. QualityMetrics puts a number on it: one windowed FFT of a shifter's output against the known target fundamental, reduced to THD+N (energy outside the fundamental) and the sharper question, artifact energy. Energy outside the fundamental's entire harmonic comb. A clean shift has real energy at its harmonics, just none outside them.

Real numbers: a 220Hz test tone through each engine's actual shifter class, swept ±12 semitones. The same synthetic-signal / real-code / numeric-threshold technique every other test on this page uses.
the definitions
THD+N%100 · √((totalEnergy − fundamentalEnergy) / fundamentalEnergy). Standard AES17-style ratio, relative to the fundamental alone
artifact energy%100 · √((totalEnergy − harmonicEnergy) / totalEnergy). Energy outside every harmonic in the whole comb
why bothTD-PSOLA at −12st: THD+N is undefined (the true fundamental nearly vanishes), yet artifact energy is 0.57%. As clean as unison. Either number alone would mislead.

The phase vocoder drops any bin that would land above Nyquist instead of wrapping it. Structural anti-aliasing, and it shows: clean across the whole range. TD-PSOLA breaks down asymmetrically at the extremes: severe and broad at +12 semitones, narrow (a fundamental collapse) at −12. Varispeed's resampler has no anti-aliasing pre-filter by design, same as physical tape, and a real, shift-dependent residual from that plus its own cubic-Hermite interpolation error still climbs toward the extremes. Most of what this chart used to show here, though, was a real, since-fixed block-rate bug rather than that inherent cost, see the Listen section below for the fix.

This metric still can't score one thing, structurally. It only ever uses a stationary test tone, so it can't expose an artifact that depends on real voice's own natural jitter the way TD-PSOLA's persistent crackle did. That artifact has since been root-caused and mostly fixed by direct instrumentation against real vocal audio instead. See the Listen section below for the fix and its small, disclosed residual.

06 · listendeep dive

The same clip, four engines, your ears

Everything above this point is a number or a diagram. This section plays real audio instead, one 22-second clip corrected into G major, run through all four engines. The three C++ engines, Corrector, PSOLACorrector, and VarispeedCorrector, use the plugin's 420ms "Smooth" retune-speed glide. Rust has no such control, so its render runs at its only mode, instant-snap. Every render calls each engine's actual production code, block by block, the same way the plugin's worker thread (or pitch-cli's) runs it live.

Rendered offline: two small render tools, cpp-plugin/benchmarks/RenderDemoAudio.cpp for the three C++ engines and crates/pitch-core/examples/render_demo_audio.rs for Rust, each feeding a WAV through the corrector at its real block size and calling the identical process() path the live plugin/CLI uses. The Rust render uses pitch-cli's real defaults (block size 2048, 50ms analysis window).
TD-PSOLA and Varispeed historically carried real, audible artifacts here, matching the quality-metrics data above (99.18% artifact energy for TD-PSOLA at +12 semitones, a 22-30% baseline for Varispeed at every shift). Both were known, actively-investigated limitations of these experimental engines. The phase vocoder's design resists this class of artifact structurally, and it remains the plugin's default engine. Further investigation, below, found and fixed a much larger cause on both engines than originally understood.
A shared bug across two unrelated engines. Closer listening found a persistent roughness, roughly an octave below the fundamental, tracking the singer's pitch, with the same character on TD-PSOLA and Varispeed despite them being structurally unrelated algorithms. That similarity was the clue. The cause wasn't in either pitch-shifting engine. It was the pitch detector all three engines share, which occasionally locks onto a note's second harmonic instead of the true fundamental, and since all three engines run the same input through an identical, deterministic detector, they all get the same wrong reading at once, biasing the correction by roughly an octave on real, correctly-pitched audio. The phase vocoder gets the same bad reading but isn't audibly affected, since its shifting method spreads the correction across many overlapping analysis windows, smoothing out a single bad reading instead of applying it as a sharp jump. Fixed by checking the detector's own confidence for each reading and falling back to the last trustworthy value when it's low. Confirmed with a small standalone probe, PitchDetectorOctaveProbe.cpp, built to run only the shared pitch detector against this real vocal clip and print its confidence per reading, rather than a synthetic test tone.
The real cause of the persistent roughness on TD-PSOLA. After the fix above shipped, the persistent roughness was still there, unchanged. That first fix caught a real but smaller, separate bug. A first guess, that the real problem was a periodic artifact tied to the plugin's internal processing block size, was tested directly by re-rendering this same clip at different block sizes (an override added to the render tool above) and checking whether the artifact's frequency moved to the exactly predicted new value. It did, three times running, but the effect mattered far more for Varispeed than for TD-PSOLA, and fixing it on TD-PSOLA changed nothing audible. The real cause was found by instrumenting TD-PSOLA's grain-placement code directly against this real vocal clip rather than a synthetic tone, and it turned out to be a numerical instability. The code located each grain's read position by dividing an ever-growing sample count by the detected pitch period, and that period shifts slightly every processing block from ordinary detection noise, so even a tiny shift in the divisor produced large read-position jumps, recurring roughly 24 times a second throughout almost the entire clip. Fixed using a standard technique from granular synthesis and audio resampling. Instead of recomputing the read position from an ever-growing absolute position each time, it's now tracked as a running total that only ever moves in small, bounded steps.
A known, disclosed limitation that remains on TD-PSOLA. A small, subtle crackle is still audible on TD-PSOLA at two moments in this clip, both landing on moments where the singer's pitch genuinely and quickly changes within a single processing block, unrelated to the bad detector readings above. A plausible explanation, not yet confirmed by targeted measurement, is that the fix above smooths pitch changes evenly across a whole processing block, which works well for ordinary block-to-block variation but not for a real vocal transition that fast, so a brief mismatch can still occur right at the transition. A second attempt at fixing this, rejecting implausibly large pitch jumps outright, was implemented, measured, and reverted in the same round of work. The read-position tracking above builds on its own history, so rejecting even a correct reading permanently shifted grain placement for the rest of the render, and both a direct audio comparison and listening back confirmed the whole clip got worse overall. Left open rather than shipped half-fixed.
Varispeed's own block-rate artifact, fixed the same way. The block-size test above was genuine for Varispeed too, and mattered far more there than for TD-PSOLA. Re-rendering the same clip at different block sizes and re-checking the artifact's frequency against the exactly predicted value, at three different sizes, found the mechanism directly. Varispeed's shift stage computed a single ratio once per processing block and used that one constant value for its entire duration, so its internal read rate took a genuine step at every block boundary. Fixed the same way as TD-PSOLA above, ramping that ratio smoothly across each block instead. A second, separate, more direct bug turned up in the same code while checking whether that first fix was enough. A click-suppression fade meant to run only right before a genuine gap in the audio was computing its fade window unconditionally, so in ordinary healthy playback it quietly faded the last few milliseconds of every single block toward silence and then ramped back up at the start of the next one, an unconditional, periodic dip exactly at the block rate. Fixed by only fading when there's an actual shortfall to anticipate. Re-checked at three block sizes again after both fixes, this time with no measurable frequency shift at all, the exact opposite of the result that first confirmed the bug. An unrelated, independent spectral-purity check (QualityMetricsTests.cpp) agreed. Varispeed's baseline artifact energy at unison dropped from about 23% to about 0.6%, now matching TD-PSOLA and the phase vocoder's own clean baseline almost exactly. A smaller, real remainder at larger shifts is expected and already disclosed elsewhere on this page. Varispeed's resampling stage has its own accepted, unrelated interpolation error that scales with shift amount.
A known, disclosed limitation that remains on Varispeed. A subtler version of the same character is still faintly audible here. Checked directly rather than guessed at. The click-suppression fade above only fires now on a genuine shortfall, and a real shortfall still happens occasionally, on about 1.5% of processing blocks in this clip, with individual gaps up to around 30 milliseconds. These are legitimate shortfalls the fade is correctly responding to, not a return of the earlier unconditional bug. The more interesting open question is why the underlying two-stage pipeline runs short at all on those blocks, a buffering question rather than a fade-logic one, and it wasn't chased down further given the time available before this needed to ship. Same disclosure standard as TD-PSOLA's own remaining residual above.
